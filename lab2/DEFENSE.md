# DEFENSE — Завдання 2: Вимоги та Use Cases

## Намір і критерії (1–2 речення)

Мета завдання — сформулювати вимоги до Wishlist Service у форматі EARS, описати User Stories і Gherkin-сценарії та забезпечити трасованість між вимогами й Use Cases
Критерії успіху: вимоги є зрозумілими й перевірюваними, діаграма містить акторів та зв’язки `include`/`extend` і узгоджується з моделлю даних із попередньої лабораторної роботи.

## Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення

- **REQ-10 — конфіденційність бронювання.** Вимога передбачає, що власник списку не бачить особу, яка забронювала товар. Відповідність уточнено в User Stories, Gherkin-сценарії та матриці трасованості: перевірка пов’язана з переглядом списку власником (UC-02). Коміт-виправлення: `feat: created reqiered project structure`.
- **REQ-12 — надсилання запрошення.** Для запрошення до публічного списку додано зовнішнього актора Email Service та Use Case UC-09. Вимогу й сценарій узгоджено з діаграмою; поведінку в разі недоступності сервісу визначено як питання для подальшого уточнення. Коміт-виправлення: `feat: created reqiered project structure`.
- **Трасованість вимог і сценаріїв.** Перевірено зв’язки між REQ, User Stories, Gherkin-сценаріями та Use Cases, щоб уникнути невідповідностей у посиланнях і позначеннях покриття. Коміт-виправлення: `feat: created reqiered project structure`.

## Ключове рішення — які альтернативи зважив і чому обрав цю (ADR)

Для надсилання запрошень розглянуто два варіанти: реалізувати надсилання всередині Wishlist Service або використати зовнішній Email Service. Обрано зовнішній сервіс, оскільки він відокремлює доставлення листів від основної бізнес-логіки та дає змогу показати інтеграцію із зовнішнім актором на Use Case Diagram.

Також для бронювання обрано модель, у якій активне бронювання зберігається в Reservation, а скасування видаляє відповідний запис. Це узгоджується з попередньою моделлю даних, у якій історія бронювань і статус скасування не зберігаються.

## Перевірка — узгодженість із попередньою моделлю (як перевірив)

Порівняно вимоги й Use Cases із моделлю даних лабораторної роботи №1. Перевірено відповідність основним сутностям User, Wishlist, WishlistItem і Reservation та бізнес-правилам: доступ до приватних списків лише для власника, бронювання товарів із публічних списків, заборона бронювати власні або завершені товари, унікальність активного бронювання та автоматичне скасування бронювання після завершення товару.
